# 向导式配对与 UI 重设计

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把当前"四档平铺、逐档手点电源测试"的配对方式,改成一键向导式配对:自动逐组试电源、锁定后逐个验证功能键、无反应键标未定义,最终生成一个完整校准档存入 NVS;同时按此交互重排 web 前端 UI。

**Architecture:** 固件侧新增一个可主机自测的向导状态机(wizard core),由 REST 端点驱动步进;校准结果(23 键 keymap)落 NVS,取代原来只存 profile_id 的配对。前端把配对区改成全屏向导流程(方案 A:居中大卡片、单键聚焦、双大按钮),遥控器页按校准档渲染(未定义键灰掉)。

**Tech Stack:** ESP-IDF v6.0.3 / C++ 固件、FreeRTOS、RMT(已有)、NVS(已有)、纯 HTML+JS 前端(已有)、host self-test(项目既有模式)。

**Spec:** `docs/superpowers/specs/2026-10-25-guided-pairing-design.md`

## Global Constraints

- **不伪造红外码**:任何键的码值要么来自内置信号库的真实表,要么是 0xFF(未定义)。校准结果里"没反应"的键必须落 0xFF,绝不猜测填值。
- **主机可测**:向导状态机必须写成无 IDF 依赖的纯逻辑(头文件内 `static inline` 或独立 .c),用 `cc -I main -DWIZARD_SELFTEST` 可编译运行,输出 `WIZARD_SELFTEST_PASS`。
- **NVS 键名 ≤15 字符**:新增的 NVS key 必须满足。
- **23 键布局不变**:`IR_KEY_COUNT`、`WIRE_NAMES`、`web_key_name` 顺序不动,前端 KEY_LAYOUT 与固件保持一致。
- **数字键 0-9 直接继承信号组原生码,不验证**(用户已确认)。
- **只验证功能键**(用户已确认 13 个:POWER/VOL±/CH±/MUTE/MENU/EXIT/OK/方向四键),不逐个验证数字键。

## Review Focus

- **中断/取消**:用户在向导中途关闭网页、断热点、重开页面,向导状态必须可恢复或可重置,不能卡死或残留半档。**裁决:取消/重启保留旧配对档;NVS 只在完成时写入。**测试:已有旧档 + 重新进入向导 → 任意步骤取消 → 旧档仍可遥控(回到遥控器视图),向导入口仍可再次进入。
- **全组无反应**:所有信号组电源键都没反应时,向导必须给出明确终点("没有匹配的信号组"),而不是死循环或空转。**裁决:电源键无码(0xFF)的组直接视为无匹配。**测试:无任何组匹配 → 状态机终止 no_match。
- **无反应键 = 0xFF 传播**:校准结果里未定义键必须从向导 → NVS → GET /api/status → 前端渲染全程一致(灰键、发送时跳过),不能被当成有效码发送。**裁决:无码功能键自动跳过标未定义,不显示该键步骤。**测试:0xFF 键发送返回 undefined 错误且不发 IR;锁定的组原生有 0xFF 的功能键在向导步骤中被跳过、keymap 中为 0xFF。
- **重复配对**:已配对后再次进入向导,旧校准档必须被完整覆盖(无残留键),旧 profile_id 配对也要被新校准档取代。测试:配对 A → 重新配对 B → 只能看到 B 的结果。
- **宏与校准档的交互**:宏录制/回放基于当前校准档;校准档重建后,旧宏里引用未定义键的步骤应安全跳过。测试:重配对后播放旧宏不崩溃、未定义键跳过。

## 背景与动机

### 现状问题(实物测试暴露)

当前配对区把 4 个内置信号组平铺列出,每个都要用户手动点「电源测试」,配对成功与否全靠用户自己记忆。实物测试时发现:

1. **四档全部不响应**:即使官方海信 NEC 0x04 档的电源键,电视也无反应(接线正确、数据灯亮)。说明「用户在一堆档里猜」这个交互本身不成立——用户无法判断哪档对,只能盲试。
2. **交互负担重**:每档要单独点一次测试,配对成功后遥控器页才解锁;缺键(0xFF)的档要用户逐个发现。
3. **缺少向导引导**:成熟产品(米家、苹果 TV 遥控器匹配)的做法是"一条龙引导用户把整套键码校准出来",而不是让用户面对一个信号库目录。

### 用户诉求(逐条确认过)

- UI 重设计,学习米家等成熟 App 的配对流程。
- **向导式配对**:
  - 一开始只出现「电源键」试探。
  - 电源有反应 → 锁定该信号组,进入**下一个功能键**的验证。
  - 电源没反应 → **自动切换下一组信号**重新试电源。
  - 功能键逐个自动发送,用户只回答"有反应 / 没反应"。
  - 没反应 → 该键标未定义,不重试,继续下一个。
  - 数字键 0-9 直接继承该组原生码,不验证。
  - 全部完成 → 生成一个完整配对档存 NVS,遥控器/宏基于它工作。
- 界面布局选定 **方案 A**:居中大卡片、单键聚焦、双大按钮、圆点进度。

## 目标 / 非目标 / 反目标

**目标:**
- 一键启动的向导式配对:电源 → 功能键 → 完成校准档落盘。
- 前端全屏向导界面(方案 A),配对完成后回到遥控器页(未定义键灰掉)。
- 校准档(23 键 keymap + 来源组)持久化 NVS,取代只存 profile_id。
- 状态机可主机自测,遵循项目既有测试纪律。

**非目标:**
- 不新增信号组库内容(信号库内容与"UI 重设计"是两回事;库扩充仍走"实物测试 → 补真实码"的既定路径)。
- 不做接收/学习功能(硬件只发不收)。
- 不逐个验证数字键。

**反目标(做了即算失败):**
- 任何一个键的码被猜测填入(必须真码或 0xFF)。
- 向导中途中断后残留半档、或无法重新开始。
- 全组无反应时死循环。
- 未定义键在遥控器页看起来可点、或发送时被当作有效码。

## 决策记录(已与用户确认)

1. **向导交互**:每步 ESP32 **自动发送**当前键的信号,用户只看电视,在界面上回答「有反应」或「没反应」。
2. **电源键**:没反应 → 标记该组已试,自动切下一组重新试电源;有反应 → 锁定该组,进入功能键校准。
3. **功能键**:有反应 → 该键用该组码;没反应 → 该键标未定义(0xFF),**不重试**,继续下一个。
4. **数字键**:不验证,直接继承锁定信号组的原生码。
5. **完成**:生成完整校准档(keymap)存 NVS;之后遥控器页、宏都基于校准档。
6. **界面布局**:方案 A(居中大卡片、单键聚焦、双大按钮、圆点进度)。
7. **功能键清单**(13 个,校准顺序即此顺序):POWER, VOL+, VOL-, CH+, CH-, MUTE, MENU, EXIT, OK, UP, DOWN, LEFT, RIGHT。
8. **无反应键语义**:标 0xFF,前端灰键;发送时后端拒绝(沿用 "key undefined in profile")。
9. **取消语义**:向导取消或中途断电重启,**保留旧配对档**(NVS 只在向导「完成」时写入);设备回到之前的配对/遥控器视图。
10. **无码键处理**:信号组本身无码(原生 0xFF)的功能键,**自动跳过并标未定义**——不显示该键的验证步骤、不发送信号("已发送"提示不说谎)。若某组电源键本身就无码(如全 0xFF 的 Hisense-C 占位组),该组直接视为无匹配,跳过,不进入功能键遍历。

## 详细设计

### 1. 向导状态机(固件纯逻辑,主机可测)

新文件:`main/app/wizard_core.h`(纯逻辑,`#ifdef WIZARD_SELFTEST` 包装主机测试)。

```
状态枚举:
  WIZARD_IDLE         未在配对向导中
  WIZARD_TRY_POWER    正在试某个信号组的电源键
  WIZARD_CALIBRATE    电源已锁定,正在逐个验证功能键
  WIZARD_DONE         完成(已生成校准档)或 无匹配(终止)

向导上下文(内存):
  group_idx            当前信号组下标
  key_idx              当前验证的功能键下标(0..12)
  tested_mask          已试过电源且无反应的组位图(避免循环)
  keymap[23]           累积的校准结果(有反应/继承=组码, 无反应=0xFF)
  source_group_id      锁定的信号组
```

步进函数(纯逻辑,只推进状态,不发 IR——IR 发送由 web 层调用 `ir_send_key`):
- `wizard_start(ctx)` → 置 `WIZARD_TRY_POWER`,group=0,清空 keymap;跳过电源键无码(0xFF)的组(见决策 10),返回"应发送的键"(该组 POWER)。若所有组电源键都无码 → `WIZARD_DONE(无匹配)`。
- `wizard_answer_power(ctx, reacted)`:
  - reacted → 锁定 group,keymap 初值 = 该组全键 keymap(含数字键),置 `WIZARD_CALIBRATE`,key_idx=0,返回"应发送的功能键[0]"(POWER 已确认,故功能键从 VOL+ 开始,还是从 POWER 重新确认?见下"校准顺序"裁决)。
  - 未 reacted → 置位 tested_mask[group],group++ 到下一个**未试过且电源键有码**的组;若无 → `WIZARD_DONE(无匹配)`;否则仍在 `WIZARD_TRY_POWER`,返回新组的 POWER。
- `wizard_answer_key(ctx, reacted)`:
  - 跳过该组原生无码(0xFF)的功能键:keymap[该键]=0xFF,key_idx 推进,不产生步骤(见决策 10)。
  - reacted → keymap[功能键[i]] = 该组该键码(保持不变)
  - 未 reacted → keymap[功能键[i]] = 0xFF
  - key_idx++ 到下一个功能键;13 个功能键全部走完(含跳过的)→ `WIZARD_DONE(有匹配)`,产生完整 keymap;否则返回下一个**可发送的**功能键。
- `wizard_cancel(ctx)` → 复位到 `WIZARD_IDLE`,丢弃上下文。**不触碰 NVS,旧配对档保留(见决策 9)。**

**校准顺序裁决**:用户说"电源有反应后逐个进入对应组的功能键"。电源已在锁定环节验证,功能键校准从**第 2 个**(VOL+)开始,POWER 不再重复确认。13 个功能键清单仍完整(用于定位 key_idx),但校准仅执行 POWER 之后的 12 个。(若实现希望简单,也可把 POWER 也当普通功能键再确认一次——不推荐,用户明确"电源有反应后"即锁定。)

### 2. NVS 存储(校准档)

沿用 `pair` 命名空间(键名 ≤15 字符):

- 新 key `pair_calib`(blob,≤23 字节):校准后的 23 键 keymap(位置即 IR_KEY_t 序号)。
- 新 key `pair_group`(u8):锁定的信号组 id(来源组,保留用途)。
- 旧 key `pair_profile`(u8)保留兼容读取:**若存在旧 profile_id 且无校准档**,视为"旧式配对"(用该组完整 keymap);一旦重新走向导生成校准档,`pair_calib` 覆盖、`pair_profile` 可废弃。

读取优先级:`pair_calib`(校准档)→ 否则 `pair_profile`(旧式组配对)→ 否则未配对。

**写入时机**:NVS 只在向导「完成」时写入 `pair_calib` + `pair_group`;取消/重启不写、不擦。旧 `pair_profile` 在完成时一并清除(否则重启后它会作为旧式配对"复活")。

**兼容迁移**:设备是全新烧录,但为了不破坏已有测试与首次配对,保留旧 key 的读取路径。

### 3. REST API

沿用现有 `/api/*` 风格,新增/调整:

- `GET /api/status`:新增 `wizard` 字段,携带向导当前状态(`{"state":"idle|try_power|calibrate|done","group_id":..,"key":"VOL+"}`),前端据此决定渲染向导视图还是遥控器视图。
- `POST /api/pair/start`:启动向导 → 返回向导首步(组 0 的 POWER),并触发发送。
- `POST /api/pair/answer`:`{"reacted":true|false}` → 步进;返回下一步要发送的键(或 `{"done":..}` / `{"no_match":true}`)。
- `POST /api/pair/cancel`:取消向导,恢复未配对。
- 移除/停用旧的「电源测试 + 就用这档」专用按钮语义(其能力由向导覆盖)。

响应与现有错误码一致("empty body"/"invalid body"/"invalid id" 等),前端 SERVER_ERRORS 映射沿用。

### 4. 前端 UI 重排(index.html)

**整体结构**(单页,三个视图切换,类似现有分区但重排):

1. **未配对 + 向导入口**:整页引导卡——"开始配对"大按钮 + 一句说明。不展示信号库目录。
2. **配对向导视图**(方案 A,全屏):
   - 顶部细进度条 / 圆点(组号 + 键进度)
   - 居中卡片:大字显示当前键名(电源 / 音量+ …),副文案提示(如"电视音量是否增大?")
   - 两个大按钮「有反应」(绿)/「没反应」(灰)
   - 顶部角落「取消」
   - ESP32 自动发送时显示轻提示("已发送信号 · 请看电视")
3. **遥控器视图**(配对完成后):
   - 顶部显示已配对来源组名 + 「重新配对」入口
   - 按键网格:未定义键(0xFF)灰掉、点击提示;宏区保留原逻辑。
   - 23 键 KEY_LAYOUT 不变。

**前端不持有状态机**:每次 `answer` 由后端返回下一步,前端只渲染+提交;页面刷新后从 `/api/status.wizard` 恢复。

### 5. 主机自测

新增 `main/app/test_wizard_core.c`(`#ifdef WIZARD_SELFTEST`),用 `cc -I main -DWIZARD_SELFTEST` 编译运行。覆盖:
- 电源有反应 → 锁定 → 逐个功能键有反应 → 生成全码 keymap。
- 电源没反应 → 逐组前进 → 全组无反应 → `no_match` 终止。
- 功能键没反应 → 该键 0xFF → 继续下一个。
- 中途取消 → 回到 IDLE。
- 重新配对覆盖旧结果。

### 6. 不动的部分

- `ir_encoder`(RMT/NEC 时序):已核实正确,不改。
- `ir_db` 信号库内容:本次不改(库扩充是独立后续)。
- `macro_engine` / 宏 UI:宏仍基于校准档发送,未定义键发送时后端跳过;宏的录制/保存/回放逻辑不变。
- 数字键:继承组码,不验证。
